Validation
==========

The port is tested against the original Fortran in three tiers, each
with a sharply defined comparison target. The test suite (104 tests)
runs all of them; the fixtures are generated by the ``tools/`` scripts
from an instrumented build of the original model.

Tier 1 — per-routine golden tests
---------------------------------

Every routine of the atmospheric time step (13 in all) is compared
against the full Fortran state captured before and after that routine,
at several warm states. Two oracles are used:

* the **standard single-precision build**, matched with float32-mode
  init constants to its own noise floor;
* a **double-precision build** (``-fdefault-real-8``), which shares
  every bit of state and every constant with the port — agreement is
  required at solver/libm roundoff, measured at :math:`\le 2\times
  10^{-14}` relative across all routines. Any porting error fails this
  by many orders of magnitude.

Tier 2 — trajectory shadowing
-----------------------------

Free 30-day integrations (2160 steps) from a warm state track the
bit-deterministic double-precision Fortran at accumulated float64
roundoff: RMS :math:`T_1` difference grows from :math:`3\times10^{-14}`
to only :math:`9\times10^{-13}` K, within ~3x of a Fortran twin seeded
with a one-part-in-:math:`10^{15}` perturbation (a last-bit change).
A from-nothing cold start — the full ``bndinit``/``varinit`` init
sequence — races a fresh Fortran cold start at the same level. The
netCDF boundary machinery reproduces the Fortran's daily SST and albedo
**bitwise**, including mid-month bracket transitions.

Notably, the twin experiments show this fixed-SST model is strongly
damped: a last-bit perturbation does *not* grow over 30 days. Shadowing
is therefore a sharp test — there is no chaos for porting errors to
hide behind.

Tier 3 — climate statistics
---------------------------

A 10-year cold-started control is compared with a Fortran control over
the same window, judged against the correct null: a *second Fortran
member* over the same window (pure internal variability). In the
heritage (f32) build, all 12 archived fields sit at the null on every
metric — area-weighted global/tropical means, annual-map RMS, pattern
correlation, interannual variance ratio.

The f32/f64 build difference
----------------------------

The two Fortran builds are genuinely different models. The polar
filter's row extent is computed as :math:`js = (1 - 60/Y_B)\,n_y/2`,
whose exact value on the standard grid is exactly 5: REAL*4 arithmetic
gives 4.99999952 → **4 filtered rows**, REAL*8 gives 5.000000000000001 →
**5 rows** (the code's stated intent, "filter poleward of 60°"). The
float32 lookup tables add smaller offsets amplified by
:math:`\epsilon_c C_{pg}`. In a 10-year control this build difference
shifts the global hydrological cycle coherently by ~0.13 %
(:math:`\Delta` Prec :math:`\equiv \Delta` Evap :math:`\approx 0.09` W
m\ :sup:`-2`, :math:`\Delta T_1 \approx -0.03` K), concentrated at high
northern latitudes — a quantified artifact of single-precision
truncation in the original model, not of the port.

Other Fortran quirks found and pinned by tests
----------------------------------------------

* ``getbnd`` is not idempotent on mid-month bracket days (a same-day
  second call corrupts the interpolation brackets with next month's
  data). The port's rule: one boundary update per model day.
* The Fortran carries two inconsistent mid-month conventions —
  calendar.F90's ``midmonth`` table says Feb = day 45, but the boundary
  readers use ``julian(mm15)`` = 46. The port uses julian anchors.
* Boundary interpolation is valid at the coupling-interval midpoint,
  ``day + ndays/2``.
* The AB3 history slots rotate write→oldest: :math:`r_{n-1}` lives at
  slice :math:`(w+1) \bmod 3`.
* The Fortran default :math:`\epsilon_c` is the decimal literal
  ``0.00013888889``, not :math:`1/7200` (an :math:`8\times10^{-9}`
  relative difference — visible in cold-start races).
* The Fortran restart file is inexact (omits the ABL warm start); the
  port's restarts round-trip bit-identically.

Performance guardrail
---------------------

The Numba kernels are required to be **bit-identical** to the NumPy
reference path: no fastmath, per-element operation order preserved,
reductions left to NumPy (pairwise summation), powers above 2 evaluated
by NumPy (Numba's ``pow`` never bit-matches NumPy's). The golden and
shadowing tests gate every optimization.
